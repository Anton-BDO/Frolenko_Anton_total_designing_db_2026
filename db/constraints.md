## Ловушки

### Ловушка 1: `payment` — неполная сущность

**Какие атрибуты добавил в `payment` и почему** (BR-8.2):

В ERD у `payment` только `payment_id` и `order_id`. Добавлено по BR-8.2 (попытка оплаты имеет тип, сумму, идентификатор транзакции, дату/время, статус):

- `payment_type payment_type NOT NULL` — тип оплаты попытки (BR-8.2);
- `amount numeric(12,2) NOT NULL` — сумма попытки (BR-8.2, BR-8.4);
- `transaction_id uuid NOT NULL UNIQUE` — внешний идентификатор транзакции, уникален (BR-8.3). Тип `uuid` вместо `varchar`: идентификатор внешний и уникальный (BR-8.3), uuid гарантирует это конструктивно; дополнительно проходит проверку B.4 (все колонки вида `%_id` — uuid);
- `payment_timestamp timestamp NOT NULL` — дата/время транзакции (BR-8.2);
- `status payment_status NOT NULL` — статус попытки (BR-8.2).

**Где хранится тип оплаты — `payment` или `order`** (BR-8.6):

В `payment`. BR-8.6: тип оплаты относится к попытке, а не к заказу — у одного заказа может быть несколько попыток с разными типами (карта не прошла → наличные при получении). Поэтому колонки типа оплаты в `"order"` нет.

Дополнительное зафиксированное решение по `payment`: BR-11.7 фиксирует объём `payment` = `value * 5` строк — ровно столько, сколько заказов. Диапазон «1–3 попытки на заказ» при 50 заказах дал бы 50–150 строк и нарушил бы C.3 чек-листа. Поэтому на каждый заказ генерируется ровно одна попытка (успешная, сумма = `total_amount`): это допустимый край диапазона 1..3, он удовлетворяет BR-8.1 (ровно одна успешная), BR-8.4, BR-11.7 и проверке C.3.

Дополнительно по оплатам:

- частичный UNIQUE-индекс BR-8.1 гарантирует «не больше одной успешной попытки на заказ»; «не меньше одной» сознательно не гарантируется — заказ рождается без оплат (`pay_status = 'ожидает'`), попытка появляется позже;
- агрегированный `pay_status` заказа (BR-8.7) пересчитывается триггером `payment_pay_status_change` (AFTER INSERT/UPDATE/DELETE на `payment`, файл `004_triggers.sql`): есть успешная попытка → `'оплачен'`; успешной нет, но есть любые попытки → `'ошибка'`; попыток нет → `'ожидает'`. Изменение или удаление попытки не может оставить заказ с устаревшим статусом;
- изменение `order_amount` при наличии попыток оплаты запрещает триггер `order_amount_freeze` (BR-8.4): сумма попытки фиксируется в момент оплаты и не должна расходиться с `total_amount` заказа.

### Ловушка 2: `order.address_id` — принадлежность клиенту (BR-7.4)

**Как обеспечено, что адрес доставки принадлежит клиенту:**

Составной FK. В `client_address` пара `(client_id, address_id)` — составной PK (BR-2.5), что само по себе уникальный ключ. В `"order"` добавлено:

```sql
CONSTRAINT order_client_address_fk
    FOREIGN KEY (client_id, address_id) REFERENCES client_address (client_id, address_id)
```

Теперь заказ можно вставить только с парой «клиент + его адрес» из `client_address`. Декларативное решение сильнее триггера: невозможно обойти ни с каким статусом проверок целостности, работает и при прямых INSERT-ах.

### Ловушка 3: `order_structure` — один ресторан в заказе (BR-7.3)

**Как обеспечено, что все блюда из `order.restaurant_id`:**

Триггер `order_structure_restaurant_check` (BEFORE INSERT OR UPDATE на `order_structure`, файл `004_triggers.sql`): проверяет, что ресторан блюда позиции совпадает с рестораном заказа, иначе — ошибка.

Декларативный вариант (техническая колонка `order_structure.restaurant_id` + два составных FK на `"order"(order_id, restaurant_id)` и `product(product_id, restaurant_id)`) рассматривался и **отвергнут**: эта колонка функционально определяется `order_id` — частью составного PK `(order_id, product_id)`, то есть давала бы частичную зависимость неключевого атрибута от части ключа, прямое нарушение 2НФ.

Цена триггерного решения — необходимость запретить смену ресторана у заказа и блюда, на которые уже есть позиции (иначе триггер позиций стал бы «отставать» от уже вставленных строк). Это делают два триггера (файл `004_triggers.sql`):

- `order_restaurant_freeze` (BEFORE UPDATE OF `restaurant_id` на `"order"`) — запрещает менять ресторан заказа, у которого есть позиции;
- `product_restaurant_freeze` (BEFORE UPDATE OF `restaurant_id` на `product`) — запрещает менять ресторан блюда, которое входит в позиции заказов.

### Ловушка 4: `review` — полиморфизм (BR-9.1)

**Как реализована валидность `review.entity_id`:**

Полиморфизм: `entity_id uuid NOT NULL` + `entity_type review_entity_type NOT NULL`, FK на `entity_id` нет — одним FK нельзя сослаться на три таблицы (`product`, `restaurant`, `"order"`). Валидность обеспечивает триггер `review_entity_check` (BEFORE INSERT OR UPDATE, файл `004_triggers.sql`): по `entity_type` проверяет существование сущности в соответствующей таблице и падает с внятой ошибкой.

Дополнительно тот же триггер проверяет связность отзыва с заказом по BR-9.2 (отзыв оставляет клиент о блюде/ресторане/заказе из своего заказа):

- `client_id` отзыва обязан совпадать с `client_id` заказа — отзыв на чужой заказ не пройдёт;
- для `entity_type = 'блюдо'`: блюдо обязано входить в состав заказа (есть в `order_structure` этого заказа);
- для `entity_type = 'ресторан'`: `entity_id` обязан совпадать с `restaurant_id` заказа;
- для `entity_type = 'заказ'`: `entity_id` обязан совпадать с `order_id` отзыва.

Нормализация (три отдельные таблицы отзывов или три nullable-FK колонки) отвергнута: нарушает единообразие обработки (BR-9.5 — единый UNIQUE на `(order_id, entity_type, entity_id)`, триггер `rating_change`, выборки аудитора по `review`), усложняет схему без выигрыша в целостности — проверка существования и связности вынесена в один компактный триггер.

## Нормализация (3НФ)

Все 12 таблиц — в 3НФ:

- каждая таблица описывает один тип сущности, PK — uuid; все неключевые атрибуты зависят от полного ключа (2НФ не нарушается — составные PK `client_address`, `order_structure`, `courier_pay`, `review` не порождают частичных зависимостей);
- транзитивных зависимостей нет: справочники (`address`, `product_category`, `client`, `courier`, `restaurant`) не хранят атрибутов друг друга; заказ хранит только FK на справочники, не их поля.

Особые случаи:

- `order.commission`, `order.total_amount` — вычисляемые (BR-1.4, BR-7.10). Решение: `GENERATED ALWAYS AS ... STORED` — значение физически хранится (быстрое чтение, индексация CHECK-ом `total_amount >= 1000`), но единственный источник истины — `order_amount`; рассинхрон исключён на уровне механизма, а не дисциплины;
- `product.rating`, `restaurant.rating` — **осознанная денормализация**: агрегаты по отзывам (BR-9.6) для скорости чтения (рейтинг читается на каждой выдаче меню/ресторанов, а меняется редко). Поддерживаются автоматически триггером `rating_change` (INSERT/UPDATE/DELETE на `review`), что исключает рассинхрон; при нуле отзывов — NULL (BR-9.7);
- `review.entity_id` + `entity_type` — полиморфизм (см. ловушку 4). Транзитивных зависимостей не создаёт (атрибуты сущности-цели в `review` не дублируются);
- вариант с технической колонкой `order_structure.restaurant_id` под составные FK ловушки 3 рассматривался и **отвергнут**: колонка функционально определялась бы `order_id` — частью составного PK `(order_id, product_id)`, то есть давала частичную зависимость и нарушала 2НФ. Итоговая `order_structure` содержит только `(order_id, product_id, quantity)` и находится в 3НФ без оговорок.
